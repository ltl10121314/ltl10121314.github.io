Kubernetes 微服务与中间件架构设计

系统与中间件 / Kubernetes 阅读约 24 分钟访问量—次

整体架构设计

在 Linux 服务器上，使用
Kubernetes（K8s）管理业务微服务、数据库、缓存和消息中间件，建议采用：

Kubernetes 统一编排 + 微服务分层部署 + StatefulSet 管理有状态服务 +
持久化存储 + Ingress 统一流量入口。

核心原则：业务微服务和基础设施中间件可以统一由 K8s
管理，但部署方式、存储方式和扩缩容策略不能完全一样。

组件 推荐部署方式 重点

Spring Boot 微服务 Deployment 多副本、滚动升级、健康检查

MySQL StatefulSet 或 持久化、备份、主从复制、故障切换
Operator；也可部署在集群外

Redis StatefulSet 或 Operator 按单机、主从、Sentinel、Cluster
选择

Kafka StatefulSet / Operator Broker 身份、独立磁盘、数据可靠性

RocketMQ StatefulSet / Operator Broker 持久化、复制和主从切换

Nacos Deployment 或 StatefulSet 按部署模式及持久化需求选择

Elasticsearch StatefulSet / Operator 节点角色、磁盘、JVM、分片和快照

Linux 服务器如何部署 Kubernetes

Kubernetes 不是一个 Docker
容器，而是一套容器编排系统。生产环境需要规划控制面、工作节点、网络、存储和高可用。

Linux 集群节点规划

示例：三个控制面节点和四个工作节点。

服务器 角色 部署内容

k8s-master-01 Control Plane API
Server、Scheduler、Controller
Manager、etcd

k8s-master-02 Control Plane 高可用控制面

k8s-master-03 Control Plane 高可用控制面

k8s-worker-01 Worker Spring Boot 微服务

k8s-worker-02 Worker Spring Boot 微服务

k8s-worker-03 Worker 数据库、消息中间件

k8s-worker-04 Worker 数据库、消息中间件

这是逻辑规划。实际部署可以通过节点标签、污点（Taint）和容忍度（Toleration）控制
Pod 的调度位置。也可以根据资源规模混合部署应用和中间件。

Kubernetes 核心组件

组件 作用

kube-apiserver 集群 API 入口，所有控制操作通过 API
Server 进行

etcd 保存 Kubernetes 集群状态数据

kube-scheduler 为待调度 Pod 选择节点

kube-controller-manager 运行控制器，持续协调实际状态与期望状态

kubelet 管理节点上的 Pod 和容器

kube-proxy 在常见网络方案中实现 Service
网络转发；部分 CNI 可替代其数据面功能

containerd 容器运行时

CoreDNS 集群内部 DNS 服务发现

生产环境要考虑控制面高可用、etcd 备份、节点资源规划和集群升级策略。

Namespace 命名空间规划

不要把所有业务和中间件都放在 default 命名空间。可以按环境和职责划分：

Namespace 的价值：

  1. 逻辑隔离 dev、test、prod 环境。
  2. 分开管理业务服务和数据库权限。
  3. 可以按 Namespace 设置 ResourceQuota 和 LimitRange。
  4. 可以通过 NetworkPolicy 限制网络访问（前提是网络插件支持）。
  5. 可以分别管理应用和中间件的发布周期。

注意：Namespace
是逻辑隔离，不等于物理隔离，也不会自动形成完整的安全边界。

数据库和消息中间件部署

这是整个架构中需要重点设计的部分。

业务服务通常是无状态的，而数据库和消息中间件是有状态的：

  • Spring Boot Pod 删除后可以重新创建，业务数据不应因此丢失。
  • MySQL Pod 删除或重建后，数据库文件必须保留。
  • Kafka Broker 重启后，需要继续使用自己的数据目录和身份。
  • Redis 如果承担持久化任务，也需要考虑数据恢复。

常用 Kubernetes 资源：

  • StatefulSet
  • Headless Service
  • PersistentVolume（PV）
  • PersistentVolumeClaim（PVC）
  • StorageClass

MySQL

MySQL 可以使用 StatefulSet、Operator 或集群外的独立数据库服务。

上图仅表示实例与存储的关系，并不意味着 StatefulSet 自动实现了 MySQL
主从复制。

MySQL 高可用还需要额外设计：

  • 主从复制或其他复制方案。
  • 故障检测和主从切换。
  • 备份与恢复。
  • 数据一致性和恢复点目标。
  • 客户端连接入口管理。

生产环境可以考虑 MySQL Operator，或者直接使用云数据库、独立数据库集群。

建议：生产环境优先评估独立数据库集群，不要为了使用 K8s
而强行把核心数据库放进 K8s。 数据库可以运行在独立 Linux
服务器、云数据库或专门的数据库集群中，业务 Pod 通过网络访问。

Redis

根据业务场景选择部署模式：

模式 适用场景

Standalone 开发、测试或非关键缓存
Master-Replica 主从复制
Sentinel 监控与自动故障转移
Redis Cluster 分片和水平扩展

可以采用 StatefulSet 或成熟的 Redis Operator。是否需要 PVC、AOF/RDB
持久化，应根据 Redis 承担的是缓存还是重要数据存储来决定。

Kafka

三个 Broker 的示意：

每个 Broker
都需要独立的数据存储，并规划副本因子、分区、副本放置、磁盘容量和故障恢复。

建议使用 Strimzi Operator 管理 Kafka，而不是手工维护大量 StatefulSet
配置。Operator 仍然需要正确配置存储、资源、升级和备份策略。

RocketMQ

RocketMQ 可以按 NameServer、Broker 等角色规划：

Broker
需要重点考虑数据持久化、复制机制、主从切换、磁盘容量和消息保留策略。实际拓扑应结合所使用的
RocketMQ 版本及部署模式确定。

Elasticsearch

Elasticsearch 可以采用 StatefulSet 或相应 Operator
管理。生产部署需要规划：

  • Master 节点。
  • Data 节点及其他节点角色。
  • 磁盘容量和 I/O 性能。
  • JVM Heap。
  • 主分片和副本分片。
  • 快照备份与恢复。

不要简单地把所有 Elasticsearch 节点放在一个 Pod 中。

Nacos 与 Kubernetes 服务发现

一个常见问题是：Kubernetes 已经有服务发现机制，为什么还需要 Nacos？

Kubernetes 本身提供：

  • Service 服务发现。
  • CoreDNS 域名解析。
  • ConfigMap 配置管理。
  • Secret 敏感信息管理。

Nacos 提供：

  • 服务注册与发现。
  • 动态配置管理。
  • 服务健康状态管理。
  • Spring Cloud Alibaba 生态集成。

两者有一定功能重叠，可以根据项目技术栈选择：

方案 服务发现 配置管理

纯 Kubernetes Service + DNS ConfigMap + Secret
Spring Cloud Alibaba Nacos Nacos
混合架构 Kubernetes Service 或 Nacos Nacos + ConfigMap

如果项目使用 Spring Boot + Spring Cloud Alibaba +
OpenFeign，可以继续保留 Nacos。

如果是纯 Spring Boot 微服务，可以直接使用 Kubernetes Service +
CoreDNS，不一定需要 Nacos。

避免在没有明确需求的情况下，同时维护两套重复的服务注册发现体系。

存储架构：数据如何持久化

Pod
可以被删除和重新创建，因此不能简单地把数据库文件只存储在容器可写层中。

存储关系：

常见存储方案：

存储方案 适用场景

Local Persistent Volume 本地磁盘，性能较好，但与节点绑定
NFS 共享文件存储
Ceph RBD 分布式块存储
Longhorn Kubernetes 分布式块存储
云厂商 CSI 云硬盘及云存储服务

注意事项：

  • Local PV 依赖节点，节点损坏可能影响数据访问。
  • NFS 不一定适合高 IOPS 数据库负载。
  • Ceph 和 Longhorn 需要额外运维。
  • PVC 不是数据库备份。
  • 必须有独立备份、恢复和异地容灾方案。
  • MySQL、Kafka 等组件应使用满足其性能和一致性要求的存储。

监控和日志架构

生产环境不能只关注 Pod 是否处于 Running
状态，还要监控业务、数据库、消息队列和 Linux 节点。

推荐技术栈：

组件 作用

Prometheus 指标采集和存储
Grafana 指标可视化
Alertmanager 告警管理
Loki 日志存储和查询
Promtail / Grafana Alloy 日志采集
Node Exporter Linux 主机监控
kube-state-metrics Kubernetes 资源对象状态指标

重点监控：

  • CPU、内存、磁盘和网络。
  • Pod 重启次数及异常状态。
  • JVM Heap、GC。
  • HTTP 请求量、错误率和响应时间。
  • MySQL 连接数、慢 SQL、复制延迟。
  • Redis 内存、命中率和复制状态。
  • Kafka Consumer Lag、Broker 状态和磁盘。
  • RocketMQ 消息堆积和 Broker 状态。
  • Elasticsearch 集群健康、分片和磁盘。

Java 项目可以结合 Spring Boot Actuator 和 Micrometer，将 JVM、HTTP
等指标暴露给 Prometheus。

CI/CD 自动化部署

实际企业项目中，Kubernetes 通常会配合 CI/CD。

可以选择：

  • GitLab CI：代码构建和流水线。
  • Jenkins：自动化构建和部署。
  • Harbor：私有容器镜像仓库。
  • Helm：应用发布和配置模板化。
  • Argo CD：GitOps 持续交付。

生产环境建议使用不可变镜像版本，例如 Git Commit SHA
或明确的发布版本号，不要长期使用 latest。

迁移基础设施

部署 Spring Boot 微服务

使用 Deployment、Service、HPA 和 Ingress。

企业级部署

逐步引入高可用、监控告警、自动发布、备份恢复和安全策略。

Elasticsearch、Kafka、RocketMQ、MySQL 等服务会占用较多 Mac
内存，建议先迁移少量服务，不要一次全部启动。

Kubernetes 核心知识学习顺序

顺序 知识点 需要解决的问题

1 Pod 容器如何运行
2 Deployment 微服务如何部署、扩容
3 Service 微服务如何互相访问
4 Namespace 环境如何隔离
5 ConfigMap / Secret 配置和密码如何管理
6 Ingress 外部请求如何进入集群
7 StatefulSet 数据库等有状态服务如何部署
8 PV / PVC 数据如何持久化
9 HPA 微服务如何自动扩缩容
10 Helm 如何管理复杂部署
11 Operator 如何自动化管理中间件
12 Prometheus 如何监控整个集群
13 CI/CD 如何实现自动构建和部署

总结与架构建议

不要把 Kubernetes 仅仅理解成 Docker Compose 的替代品。

Docker Compose 主要解决容器编排和启动问题；Kubernetes 还要解决：

  • 集群调度。
  • 服务发现。
  • 故障恢复。
  • 自动扩缩容。
  • 存储编排。
  • 应用发布和回滚。
  • 集群监控与安全治理。

对于当前的本地环境，推荐从 ~/docker/backend/ 出发，搭建 Colima +
Kubernetes 实操环境，先部署 Nginx、Spring Boot、MySQL、Redis，再逐步加入
Kafka、RocketMQ 和 Elasticsearch。

这样可以把 Docker、Spring Boot、微服务和 Kubernetes
串成一套完整的技术体系。
